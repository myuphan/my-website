DevOps: Node.js CI/CD Pipeline

A hands-on DevOps project that provisions cloud infrastructure with Terraform, configures a server with Ansible, and deploys a Node.js sign-up/login website backed by PostgreSQL. I built and tested two different deployment methods end to end: a manual Ansible-driven deployment onto a fresh EC2 instance, and a fully automated pipeline using GitHub Actions that redeploys on every push — even after the server's public IP changes.

Overview OF WORKFLOW

🏗️ Terraform

Provisioned an AWS EC2 instance, security group, and key pair as reproducible, version-controlled code.

⚙️ Ansible

Two roles — postgres installs and secures PostgreSQL; app installs Node.js and deploys the app as a systemd service.

🔐 Ansible Vault

Encrypted database credentials so secrets never sit in plaintext inside the repo.

🔑 bcrypt auth

Hashed passwords before storage and verified logins by comparing hashes, never plaintext.

🖥️ Method 1: Manual deploy

Provisioned the server, cloned the repo onto it directly, and ran the app as a systemd service by hand.

🚀 Method 2: GitHub Actions

Automated redeploys on every push — dynamically looks up the server's current IP via the AWS API, no Elastic IP required.

🏗️ Step 1 — Provisioning with Terraform

Terraform defines the EC2 instance, its security group, and key pair as code, rather than clicking through the AWS console by hand. Running terraform apply stands up the exact same server every time — reproducible, version-controlled infrastructure.

terraform/main.tf

#user key generated on AWS
provider "aws" {
    region = "us-east-2"
    access_key = var.aws_access_key
    secret_key = var.aws_secret_key
}

#new key-pair

resource "aws_key_pair" "developer" {
    key_name = "node.js-key-pair"
    public_key = file("/home/phanumy/.ssh/ansible-key.pub")
}

resource "aws_security_group" "allow_traffic" {
    name = "allow_traffic"
    description = "allow traffic to server"

    ingress {
        from_port = 22
        to_port = 22
        protocol = "tcp"
        cidr_blocks = ["0.0.0.0/0"]
    }

    ingress {
        from_port = 80
        to_port = 80
        protocol = "tcp"
        cidr_blocks = ["0.0.0.0/0"]

    }

    ingress {
        from_port = 443
        to_port = 443
        protocol = "tcp"
        cidr_blocks = ["0.0.0.0/0"]
    }

    egress {
    from_port = 0
    to_port = 0
    protocol = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }
}

resource "aws_instance" "my_server" {
    ami           = "your-ami-id" # Replace with a valid Ubuntu AMI ID for your region
    instance_type = "your-instance-type" # Replace with your desired instance type, e.g., "t2.micro"
    vpc_security_group_ids = [
        aws_security_group.allow_traffic.id
    ]

    key_name = aws_key_pair.developer.key_name

    tags = {
        Name = "My-Node.js-EC2"
        Project = "mynode.js"
    }
}

output"instance_public_ip" {
    value = aws_instance.my_server.public_ip
}

The Project = "mynode.js" tag matters beyond bookkeeping — both the Ansible dynamic inventory and the GitHub Actions workflow later use this exact tag to find the running instance automatically, without anyone hardcoding an IP address anywhere.

⚙️ Step 2 — Configuring the server with Ansible

Ansible finds the server through a dynamic inventory that queries AWS directly, rather than a static list of IPs — since a stopped/restarted EC2 instance gets a brand-new public IP every time.

inventory/aws_ec2.yml

plugin: amazon.aws.aws_ec2
regions:
  - us-east-2
filters:
  instance-state-name: running
  tag:Project: mynode.js
hostnames:
  - node-js
compose:
  ansible_host: public_ip_address
  ansible_user: "'ubuntu'"
  ansible_ssh_private_key_file: "'/home/phanumy/.ssh/ansible-key'"

The main playbook loads an encrypted Ansible Vault for credentials, then applies two roles in order — database first, application second.

Ansible/node_service.yml

- name: Configure server and deploy Node.js app
  hosts: all
  become: true
  vars_files:
    - group_vars/all/vault.yml

  roles:
    - role: postgres
      tags: postgres
    - role: app
      tags: app

The postgres role installs PostgreSQL, creates a dedicated application database and a restricted-privilege user, switches authentication from OS-based peer to password-based md5, and creates the users table.

Ansible/roles/postgres/tasks/main.yml

- #install postgres
- name: Install acl package (required for become_user)
  apt:
    name: acl
    state: present
    update_cache: yes

- name: Install PostgreSQL
  apt:
    name: 
    - postgresql
    - postgresql-contrib
    - python3-psycopg2
    state: present
    update_cache: yes
- name: Ensure PostgreSQL is running
  service:
    name: postgresql
    state: started
    enabled: yes

#to enable to create the db, ubuntu user need to switch to postgres user and run the command, so we need to add ubuntu user to postgres group
- name: create app db
  become: true
  become_user: postgres
  postgresql_db:
    name: "{{ vault_db_name }}"
    state: present

#enable node.js to log in and modify postgres
- name: create app db user
  become: true
  become_user: postgres
  postgresql_user:
    name: "{{ vault_db_user }}"
    password: "{{ vault_db_password }}"
    db: "{{ vault_db_name }}"
    priv: "ALL"
    state: present
  


- name: Create user table
  become: true
  become_user: postgres
  postgresql_query:
    db: "{{ vault_db_name }}"
    query: >
      CREATE TABLE IF NOT EXISTS users (
        id SERIAL PRIMARY KEY,
        username VARCHAR(255) UNIQUE NOT NULL,
        password_hash VARCHAR(255) NOT NULL,
        created_at TIMESTAMP DEFAULT NOW()
      );

 #flip a default setting in pg_hba.conf to allow local password authentication for node.js     
- name: Allow local password authentication in pg_hba.conf
  lineinfile:
    path: /etc/postgresql/{{ postgresql_version | default('16') }}/main/pg_hba.conf
    regexp: '^local\s+all\s+all\s+peer'
    line: "local   all             all                                     md5"
    state: present
  notify: restart postgresql


#make sure listen on localhost since receive request from node.js app
- name: Allow app to connect via TCP (localhost)
  lineinfile:
    path: /etc/postgresql/{{ postgresql_version | default('16') }}/main/postgresql.conf
    regexp: '^#?listen_addresses'
    line: "listen_addresses = 'localhost'"
    state: present
  notify: restart postgresql

The app role installs Node.js, pulls the application code, installs dependencies, and generates two files from Jinja2 templates: the app's environment file and its systemd unit.

roles/app/tasks/main.yml

- name: Add NodeSource GPG key and repo
  shell: curl -fsSL https://deb.nodesource.com/setup_20.x | sudo -E bash -
  args:
    creates: /etc/apt/sources.list.d/nodesource.list

- name: Install Node.js and npm
  apt:
    name: nodejs
    state: present
    update_cache: yes

- name: Clone or update the application repository
  git:
    repo: "https://github.com/myuphan/Node-AWS.git"
    dest: /home/ubuntu/node-app
    version: master
    force: yes
  become: true

- name: Install npm dependencies
  npm:
    path: /home/ubuntu/node-app
    production: yes
  become: true
  become_user: ubuntu

- name: Create .env file with database connection details
  template:
    src: env.j2
    dest: /home/ubuntu/node-app/.env
    owner: ubuntu
    group: ubuntu
    mode: "0600"
  no_log: true

- name: Create systemd service file for the Node.js app
  template:
    src: app.service.j2
    dest: /etc/systemd/system/node-app.service
    mode: "0644"
  notify: restart node-app

- name: Enable and start the Node.js app service
  systemd:
    name: node-app
    state: started
    enabled: true
    daemon_reload: yes

.service file - systemd

Ansible/roles/app/templates/app.service.j2 — This file is important because it generates a template for systemd file (on EC2 server /etc/systemd/system/node-app.service) keep the app running/ systemd read node-app.service file. Node-app.service file point to index.js and routes or .env 

[Unit]
Description=Node.js Ecommerce Practice App
After=network.target postgresql.service

[Service]
Type=simple
User=ubuntu
WorkingDirectory=/home/ubuntu/node-app #instructions inside that file, telling systemd where your actual application code is, so it knows what to run.
EnvironmentFile=/home/ubuntu/node-app/.env
Restart=on-failure
RestartSec=5
AmbientCapabilities=CAP_NET_BIND_SERVICE

[Install]
WantedBy=multi-user.target

The app connected to ansible/roles/app/tasks/main.yml where indicated the location on EC2 that systemd service file is located. Systemd read the instructions in the node-app.service file to keep the app running without restarting/stopping node-app code 

[Unit]
- name: Create systemd service file for the Node.js app
  template:
    src: app.service.j2 #the template file
    dest: /etc/systemd/system/node-app.service #exact location on EC2 server
    mode: "0644"
  notify: restart node-app

AmbientCapabilities=CAP_NET_BIND_SERVICE is doing quiet, important work here — it lets the app bind to port 80 without running the whole process as root, which would otherwise be the only way for a non-privileged user to use a port below 1024.

🔑 The application: Express + bcrypt + PostgreSQL

Explaination APIs routes logic: registerRoute ( a constant) that linked to the /routes/register folder. register.js is also a mini express app that configure APIs of it own logic. When POST/register arrives your servers, express will check app.use(...) and it reaches app.use(registerRoute) because internally has a route matching POST /register. It run bcrypt/db logic and send back a response.

Node-app/Routes/register.js- a mini express app

routes/register.js hashes the password with bcrypt before it ever touches the database, and relies on a unique constraint at the database level to reject duplicate usernames cleanly:

router.post('/register', async (req, res) => {
  const { username, password } = req.body;

  if (!username || !password) {
    return res.status(400).json({ error: 'username and password are required' });
  }

  try {
    const passwordHash = await bcrypt.hash(password, SALT_ROUNDS);

    const result = await pool.query(
      'INSERT INTO users (username, password_hash) VALUES ($1, $2) RETURNING id, username, created_at',
      [username, passwordHash]
    );

    res.status(201).json({ user: result.rows[0] });
  } catch (err) {
    if (err.code === '23505') {
      return res.status(409).json({ error: 'username already taken' });
    }
    console.error(err);
    res.status(500).json({ error: 'internal server error' });
  }
});

routes/login.js never looks up a password — it re-hashes the submitted attempt and compares it against the stored hash, and returns the same generic error whether the username doesn't exist or the password is wrong, so a failed login never reveals which usernames are registered:

const result = await pool.query(
  'SELECT id, username, password_hash FROM users WHERE username = $1',
  [username]
);

if (result.rows.length === 0) {
  return res.status(401).json({ error: 'invalid username or password' });
}

const match = await bcrypt.compare(password, result.rows[0].password_hash);

if (!match) {
  return res.status(401).json({ error: 'invalid username or password' });
}

🖥️ Method 1 — Manual deployment

The first working version of this pipeline was deployed by hand, one command at a time, to prove each layer worked before automating any of it. After Terraform provisioned the instance and the postgres role was confirmed working, the application side was set up directly on the server:

ssh -i ~/.ssh/ansible-key ubuntu@<ec2-public-ip>

git clone https://github.com/myuphan/Node-AWS.git ~/node-app
cd ~/node-app
npm install

nano .env          # filled in manually with the real vault values
sudo nano /etc/systemd/system/node-app.service   # same content as app.service.j2, by hand

sudo systemctl daemon-reload
sudo systemctl enable node-app
sudo systemctl start node-app

Once the whole app role's logic was proven this way — file system, database connection, systemd, and public reachability all confirmed working by hand — the same steps were folded back into the Ansible role, so ansible-playbook node_service.yml --tags app now reproduces this exact setup automatically on any fresh instance:

ansible-playbook node_service.yml -i inventory/aws_ec2.yml --tags app --ask-vault-pass

This is Task #1 from the original project brief — a working manual deployment, reachable on port 80 by public IP, driven entirely by a single Ansible command.

🚀 Method 2 — Automated deployment with GitHub Actions

The second method removes manual SSH from the loop entirely. On every push to master, a workflow authenticates to AWS with a dedicated, read-only IAM user, looks up the EC2 instance's current public IP by its tag, then SSHes in and redeploys.

.github/workflows/deploy.yml

name: Deploy to EC2

on:
  push:
    branches:
      - master

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Configure AWS credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY_ID }}
          aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
          aws-region: us-east-2

      - name: Get current EC2 public IP
        id: get_ip
        run: |
          IP=$(aws ec2 describe-instances \
            --filters "Name=tag:Project,Values=mynode.js" "Name=instance-state-name,Values=running" \
            --query "Reservations[0].Instances[0].PublicIpAddress" \
            --output text)
          echo "Found IP: $IP"
          echo "ip=$IP" >> "$GITHUB_OUTPUT"

      - name: Deploy via SSH
        uses: appleboy/ssh-action@v1.0.3
        with:
          host: ${{ steps.get_ip.outputs.ip }}
          username: ubuntu
          key: ${{ secrets.EC2_SSH_KEY }}
          script: |
            cd ~/node-app
            git pull origin master
            npm install --production
            sudo systemctl restart node-app

Looking the IP up live, instead of storing it as a fixed secret, was a deliberate choice: stopping and restarting the EC2 instance normally assigns a new public IP, which would silently break a hardcoded deployment target. Querying AWS directly on every run means the workflow keeps working through restarts with no Elastic IP and no manual secret updates — the same problem the Ansible dynamic inventory already solves, solved again on the GitHub Actions side.

Three repository secrets make this work: AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY for a read-only IAM user scoped to AmazonEC2ReadOnlyAccess — enough to look up the instance, nothing more — and EC2_SSH_KEY, the same private key used for manual SSH access, so the workflow can authenticate to the server exactly as a human operator would.

Testing

Both methods were verified end to end, including the failure case that matters most for a project like this: stopping the EC2 instance (which releases its public IP), starting it again, and confirming the systemd service came back online automatically with zero manual intervention. Pushing a small code change afterward triggered GitHub Actions to look up the new IP, SSH in, and deploy — without updating a single secret by hand.
